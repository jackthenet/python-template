# Code structure map

`STRUCTURE.md` at the repository root is generated by `scripts/make_map.py`: the directory tree of the
repository's Python files, then a per-module section with line counts and symbols. It is a generated
artifact — produced only by the generator, never hand-edited.

## The four rules

1. **Read the map before you explore.** Read `STRUCTURE.md` before walking the tree: it answers
   "where does this code live?" without a directory walk.
2. **Regenerate when it is stale.** Check freshness with
   `uv run python scripts/make_map.py --check` (exit 1 = stale, 3 = missing); regenerate with
   `uv run python scripts/make_map.py`.
3. **Regenerate in the same commit as the `.py` change.** A commit that adds, renames, moves or
   deletes a Python file also carries the regenerated map — not a follow-up commit.
4. **On a merge conflict in `STRUCTURE.md`, take either side and regenerate.** Never hand-merge the
   generated file: resolve it by taking either side, then run the generator so the map matches the
   tree that results from the merge.

## What the generator does

- Generate mode writes the map and exits 0; `--check` only compares and never rewrites anything.
- The local `structure-map-check` hook in `.pre-commit-config.yaml` runs the `--check` mode on any
  staged `.py` file, so a stale map is caught at commit time.
- The map is not part of the workflow: no phase, gate, todo status or handoff field depends on it.
  The hook is a local commit guard, and no CI job runs the generator.

## Known limitation

A file that exists in the working tree but is untracked and not ignored is listed in the committed
map; on a fresh clone `--check` reports the map as stale, and regenerating there removes the entry.
Commit the file (or ignore it) rather than chasing the difference.
