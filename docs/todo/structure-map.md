## Goal (one line)
A deterministic, stdlib-only generator (`scripts/make_map.py`) that writes a compact `STRUCTURE.md` map of the repository, plus a short skill telling agents to read the map before opening files.

## Why
An agent entering this repo pays for exploration it rarely needs: `git ls-files` reports **522 tracked files, 323 of them `.py`, 33 701 Python lines** across 11 backend features and 5 test categories. Today the only way to learn where something lives is to walk the tree and open files (the `specify` skill's step "Search and read existing codebase files to understand current context and patterns" has no cheap input). A generated signature-level map lets an agent read one file and open only the modules it actually needs — and the map is code-generated, so it cannot drift silently the way a hand-written architecture note does.

```text
Create a script that generates a compact, deterministic structure map of this repository, plus a
thin skill that tells agents how to use it.

Goals
- Give an agent a cheap overview of the codebase, so it can read the map first and open only the
  files it needs.
- The map is generated by code, not written by hand or by an LLM. Output must be identical across
  runs on unchanged code.

Deliverables
1. scripts/make_map.py
   - Standard library only (use ast, pathlib, argparse). No third-party dependencies.
   - Walk the repo, respecting .gitignore (use git ls-files if inside a git repo, otherwise fall
     back to a built-in ignore list: .git, .venv, node_modules, __pycache__, dist, build).
   - For each .py file, output: the relative path and line count; the module docstring (first line
     only); top-level classes with base classes and their public methods; top-level functions;
     signatures with type annotations, but no bodies; first line of each docstring, if present.
   - Skip private names (leading underscore) unless --include-private is passed.
   - Files that fail to parse must not crash the script. List them with (parse error).
   - Sort everything alphabetically for stable output.
   - CLI: python scripts/make_map.py [--root .] [--out STRUCTURE.md] [--include-private]
          [--max-depth N] [--check]
   - --check exits with code 1 if the existing output file is out of date (for CI and pre-commit).
2. Output format (STRUCTURE.md), compact Markdown:
     # Repository structure
     _Generated by scripts/make_map.py. Do not edit by hand._
     ## Directory tree
     (tree view, directories only plus file names)
     ## Modules
     ### src/pkg/module.py (120 lines)
     Module summary line.
     - class `Foo(Base)`: summary
       - `bar(self, x: int) -> str`: summary
     - def `helper(a: str) -> None`: summary
   Keep the whole file small enough to fit in a context window. If it exceeds about 400 lines,
   group by package and truncate with a note.
3. skills/code-structure-map/SKILL.md
   - Frontmatter with name and a description that states when to trigger: before exploring an
     unfamiliar repo, before editing across multiple modules, or when asked where something lives.
   - Instructions: read STRUCTURE.md first, pick relevant files, open only those. If the map is
     missing or stale, run python scripts/make_map.py.
   - Keep it short (under 60 lines).
4. Automation
   - Add a pre-commit hook or Makefile target that runs make_map.py --check.
   - Add a one-line note to AGENTS.md (or CLAUDE.md) pointing to STRUCTURE.md.

Constraints
- No LLM calls inside the script.
- No hardcoded absolute paths.
- Write tests for the parser logic (pytest): nested classes, async functions, decorators,
  syntax-error files, empty files.
- Keep the code typed and under about 250 lines. Prefer small functions.

Process
1. Inspect the repo layout and existing tooling first, then briefly state your plan.
2. Implement the script and run it on this repo.
3. Show me the first 40 lines of the generated STRUCTURE.md.
4. Report anything you assumed or skipped.
```

## In scope

- `STRUCTURE.md` at the repo root, generated by the script, in the format above (directory tree + modules section), with the package-grouping/truncation rule when it exceeds ~400 lines.

## Constraints and risks
- **The 400-line budget vs. this repo's size.** ~1 405 top-level `def`/`class` statements plus ~675 methods means a naive map is ≈2 400 lines — 6× the stated budget. The "group by package and truncate with a note" rule is therefore load-bearing, not an edge case: P.2 must decide the grouping unit (top-level package vs. feature dir) and what truncation drops (bodies of symbol lines vs. whole low-value packages, e.g. `tests/`), and the spec must state the rule precisely enough to be deterministic.
- **Determinism.** `git ls-files` output order is stable but locale-dependent; sorting must be explicit on the relative POSIX path string. Windows path separators must be normalised (`as_posix()`), or the map differs between the local run and CI (`ubuntu-latest`). Line counts must come from the same bytes the parser reads (`read_text(encoding="utf-8")`, matching `scripts/check_traceability.py`).
- **Self-reference / churn.** `STRUCTURE.md` is not `.py`, so the generator never maps itself, but the pre-commit `--check` hook fails whenever any `.py` file changes without a regeneration — the hook must therefore be `pass_filenames: false`, and every change branch that touches a `.py` file has to regenerate the map in the same commit. Expect friction on every change branch (decided: check-only hook, no CI job — Q-2, 2026-10-03).
- **Quality gates that will see the new code.** `ruff check .` / `ruff format --check .` cover `scripts/` (lint job, `lint.yml`); `mypy` runs on `src/` only, so the script is not type-checked by the gate — the "keep the code typed" requirement is self-imposed unless P.2 extends mypy's scope. `deptry` already includes `scripts/` in its file filter (`.pre-commit-config.yaml`) and the script must stay stdlib-only so DEP rules stay clean. `complexipy` runs on `src`+`tests` only (`[tool.complexipy]`), so the script's own complexity is ungated.
- **Test placement vs. coverage floor.** `[tool.coverage.report] fail_under = 92` with `source = ["src/backend", "src/frontend"]` — a test file for `scripts/` adds no coverage credit and must not be written as if it did; the new tests must also pass `ruff` under the strict `select` set (`PL`, `SIM`, `B`, `C4`, `Q`).
- **Skill wording.** The skill is live agent guidance; "read `STRUCTURE.md` first" on every task would add a read to every change. The trigger conditions must stay the three the instruction names (unfamiliar repo, cross-module edit, "where does X live").
- **Instruction vs. repo conventions — three resolved by the user at P.1 (2026-10-03), one still open for P.2:** skill → `.agents/skills/` (Q-1); `Makefile target` → pre-commit local hook, check-only (Q-2); `CLAUDE.md` → `AGENTS.md` (no `CLAUDE.md` exists); output → root `STRUCTURE.md` (Q-3). **Still open:** whether the change type stays FEATURE or drops to DOCS/CHORE (see the classification note above).

## Value triage (2026-10-03, pre-workflow)
- **Overlap:** nothing in the repo generates a codebase overview. `mkdocstrings` (`mkdocs.yml`, `userdocs/api.md`) renders API docs for humans from docstrings — different artifact (a built site, per-module pages, no directory tree, no line counts, not readable as one file by an agent), so it does not cover this; the nearest existing tooling is `scripts/check_traceability.py` / `verify_spec.py`, which analyse docs, not code. The `python-best-practices` skill has a `references/structure.md` about *where code should go* (convention text), not a map of what is here. Verdict: no existing feature to extend; the smallest diff that delivers the value is one script + one skill + one hook.
- **Beneficiary:** every agent-driven change in this repo (Phases 1–6 all start by locating code), plus a human reviewer who can see the shape of a package in one file. Cost side: one generated file to keep fresh, enforced by the hook.
- **Score: 4/5** — clear, repeated value (33 701 lines, 323 modules, no cheap overview today), new capability, and a small self-contained diff; it is not 5 because the 400-line budget against this repo's size means the map's usefulness depends on a truncation policy that must be designed, and the freshness gate adds recurring friction to every change.
- **Recommendation: implement** — as one change (script + tests + skill + hook + `AGENTS.md` line), with the four convention conflicts above resolved at P.2/P.3 rather than guessed at implementation time.
